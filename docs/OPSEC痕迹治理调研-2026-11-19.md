# OPSEC 痕迹治理调研与适配方案（2026-11-19）

> 目标：减少平台在**被渗透方**（目标侧 WAF/日志/IDS/蓝队）留下的我方身份痕迹。
> 范围：授权渗透测试/SRC 场景。三路公开资料调研 + 平台代码全量痕迹源审计交叉验证。
> 关联：v0.4.88 PR #37（去品牌守卫）、PR #43（js_audit UA）已清第一轮；本文是下一阶段的系统性方案。

## 一、平台痕迹源清单（代码审计确认 ×14）

### 传输层（调研结论：WAF 三层指纹叠加=TLS + HTTP/2 + 行为，签名层只是最浅的）

| # | 痕迹 | 代码位置 | 严重度 |
|---|---|---|---|
| T1 | 原生执行器 Go 标准 `crypto/tls`：无 GREASE、cipher/extension 顺序固定 → **公开已知的 Go JA3/JA4 指纹**，Cloudflare Bot Management 暴露 `ja4` 字段可一键阻断 | `agent/tools_http.go:314` `buildHTTPClient` | 高 |
| T2 | **UA 与 TLS 指纹矛盾**：UA 报 Chrome/131，TLS 握手是 Go——蓝队经典检测点，比裸工具 UA 更醒目 | 同上 | 高 |
| T3 | 捕获模式下 go-mitmproxy 用**自己的 Go TLS 栈**重发请求（`attacker.go` 的 `ServerConn.client` 非导出字段，外部无法注入）→ 开捕获时目标看到 mitm 的 Go 指纹；关捕获纯 CONNECT 隧道时看到执行器的 Go 指纹。**两条路径都是 Go 指纹** | `traffic/traffic.go` + go-mitmproxy@v1.9.2 | 高 |
| T4 | HTTP/2 层：伪 header 顺序（Go `:method,:scheme,:authority,:path` vs Chrome `:method,:authority,:scheme,:path`）、SETTINGS 值固定、WINDOW_UPDATE 恒 1048576、无 PRIORITY | Go 标准栈 | 中 |
| T5 | DNS：走代理时 CONNECT 不本地解析（安全）；**直连回落路径本地解析**，目标权威 NS 看到解析器 IP ≠ 出口 IP | `buildHTTPClient` 直连分支 | 中 |

| # | 痕迹 | 代码位置 | 严重度 |

## 二、适配方案（按效果/侵入度排序）

### P0 —— 下个版本即可上（不依赖 fork）

**P0-1 任务级统一身份 Profile（平台级机制，代码强制）**
- 新包 `opsec/`：每个任务生成一个**自洽假身份**：当前稳定版 Chrome UA（版本不写死，随 profile 库更新）+ 对齐的 Accept/Accept-Language/Accept-Encoding/sec-ch-ua/sec-fetch 头集合与顺序 + 与出口 IP 地理大致一致的语言偏好。**任务内全通道绑定同一 profile**（http_request/session_login/customtool/authcheck/PoC 脚本 UA/外部工具 UA/浏览器 MCP），跨任务轮换。
- 调研明确红线：**禁止每请求随机 UA**——随机 UA 与固定 TLS 指纹、节奏不一致反而更醒目（Malleable C2 的核心思想：整个任务一个流量模板）。
- 落点：`opsec/profile.go`（生成+校验器，类比 c2lint 防头集矛盾）→ `tools_http.go` 默认头改从 profile 取 → poc_scaffold/js_audit 模板 UA 参数化 → worker 提示词「工具 UA 一律取任务 profile」。

**P0-2 TLS 指纹伪装：bogdanfinn/tls-client**
- 选型结论（调研对比 5 个方案）：**tls-client**（BSD-3，2026-11 仍活跃，profiles 覆盖 chrome_131+，自带 fhttp fork 处理 header 顺序 + h2 SETTINGS/WINDOW_UPDATE/pseudo-header 顺序）包成 `http.RoundTripper`（可参考 juzeon/spoofed-round-tripper 的薄封装）替换 `buildHTTPClient` 的 transport。**效果：T1/T2/T4 三项一次解决。**
- 关键验证结论：CONNECT 隧道只转发字节，内层 ClientHello/h2 帧由客户端直发目标 → 经 mihomo/代理池出口后**指纹保留**，伪装在隧道内有效。
- 不选：裸 utls（要自己维护 h2 层，成本高）；CycleTLS（GPL-3.0 传染）；curl-impersonate（指纹最全但进程开销大，留作高防护目标专用通道，P2）。
- ⚠️ UA 与 TLS profile 必须同一版本系（chrome_131 profile ↔ Chrome/131 UA），否则 JA4H/行为层识破——与 P0-1 联动。

**P0-3 外部工具参数默认注入（提示词模板 + 守门规则双保险）**
- 统一 UA 覆盖进模板：sqlmap `--user-agent="$UA"`（禁裸调）、ffuf `-H "User-Agent: $UA"`、gobuster `-a`、httpx `-http-user-agent`、dalfox `--user-agent`、nmap `--script-args http.useragent=...`。
- 时序/并发收敛默认值：sqlmap `--delay` + `--threads=1`、nuclei `-rl`、ffuf `-rate`+`-t 5`、feroxbuster `-rate-limit`+`-s`、gobuster `--delay/--random-delay`、nmap `-T3 --max-rate`。
- 字典乱序（gobuster `--randomized` 等）+ 按技术栈裁剪。
- 落点：`ops_tails.go` 工具模板、`skills/src-hunting/references/*`、新增守门测试（断言模板不含裸 sqlmap/ffuf 调用）。
- **不默认开启**（调研结论）：sqlmap tamper 链（WAF 绕过用，非去特征，现场按需）、nmap `-D/-f/-T4`、每请求换 UA、nikto 全量（只 `-Tuning` 定向）。

**P0-4 载荷层卫生（提示词/模板层 + #21.2 审查层联动）**
- P1：CANARY 引导改为平台 OOB 通道（P1-2 前先约束：禁 webhook.site 等公共域名出站，可先做成拦截规则）。
- P2：载荷报错路径模板化——PoC 模板统一 try/except 把本地路径替换成 `<sandbox>` 再输出；ReviewInput.Scripts（v0.4.89）可加规则：含真实家目录路径的载荷 ASK。
- P3/P4：文件名与命名风格——poc_scaffold 文件名改「业务词+随机段」；提示词加「生成脚本用中性函数名、不写注释」的引导（sanitizer 机制化放 P1）。

### P1 —— 需要 fork/自建，第二批

**P1-1 fork go-mitmproxy**：把 `attacker.go` 的 client 换成可注入 RoundTripper（接 tls-client）→ 捕获路径（T3）指纹也伪装。运维模式同 Norma fork（go.mod replace）。这是捕获开启场景的必要项，不 fork 则「开捕获=Go 指纹」无解。
**P1-2 自建 OOB 通道**：interactsh 自托管（`-domain 业务风格域名 -wildcards`，NS 委托子域）+ worker `oast` 工具对接；禁公共 OOB 域名出站（守门规则强制）。
**P1-3 浏览器 MCP 反自动化**：launch 参数加 `--user-agent`（与任务 profile 一致）+ UA-CH 头对齐；评估 stealth 注入抹 `navigator.webdriver`。
**P1-4 时序 humanizer**：http_request 任务级 jitter（±30-50%）、会话内先 GET 首页再探测的轨迹模拟（提示词引导+执行器限速）。
**P1-5 出站载荷 sanitizer**：落盘/执行前统一洗稿——变量/函数名从业务词表重命名、去注释、multipart boundary/filename 随机化、路径抹除。直接针对 97% 代码归因研究。

### P2 —— 低优先

- curl-impersonate 外挂通道（高防护目标专用，走 bash 通道零侵入）
- DNS 强制远端解析（审计 T5：直连回落路径本地解析——走 mihomo fake-ip 或禁直连回落已有严格出口开关，实际敞口小）

### 明确不做（红线，与平台纪律一致）

- `-D` decoy / 伪造第三方地址（归因到无辜主机，违反授权边界）
- 每请求随机 UA（制造不一致指纹）
- 任何针对未授权目标的规避
