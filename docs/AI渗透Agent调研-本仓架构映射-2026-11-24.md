## 0. 一句话骨架

任务级双图（资产图 + 探索图）上的**事件驱动多 agent 闭环**：`notify → planner 派意图 → frontier → worker 领单执行并写回 → 再唤醒 planner`；引擎侧确定性机制（idle-stop、auto-finish、autopilot、coverage/depth nudge）兜住弱模型纪律；模型层是 `profile 绑定 → 任务链 → 全局` 三级选路 + llm pool 故障转移。

## 2. 五个最值得优先做的结构性改进

### 改进 1：覆盖率矩阵升级为一等公民（asset × dimension）

现状三套互不一致的口径：
- planner prompt 手写 10 类清单（agent/ops_tails.go:54）
- 引擎只按 6 类关键词正则匹配意图文本（server/coverage_nudge.go:21/58），每类每任务只提醒一次、6h 节流
- 纵深只看“资产≥50 且高危=0”一个全局判据（server/depth_nudge.go:33）
- graph_overview.coverage 只算“被 fact 碰过的资产占比”（agent/tools.go:695、db/task_assets_context.go:123）
- 意图已有 dimension 字段与 11 个归一维度（agent/dimension.go:11），但只用于去重/续跳

改法：新增按需计算的矩阵视图，join `intent(payload.dimension, asset_ids)`、`fact/finding`、`task_scope` → `asset × dimension → untested/open/running/done/zero-yield/finding`；`graphOverviewData` 输出矩阵（按资产类型折叠+Top 缺口）；`nudgeCoverageGaps` 选“价值最高且完全空白的 cell”派单；终局报告与 autopilot 续杯从同一矩阵取数。这样 prompt、引擎提醒、续杯、报告四处第一次是同一个事实。

落点：agent/dimension.go、agent/tools.go:506、server/coverage_nudge.go、server/depth_nudge.go、db/task_assets_context.go（或新增 db/coverage_matrix.go）、agent/tools_insert.go:524。验收：矩阵在 planner 态势/引擎提醒/docx 报告数值一致；FindSimilarOpenIntent 去重仍拦截重复派单。

### 改进 2：反思/自检做成图上的持久节点，而非 prompt 文案

现状 review 只在“exhausted 且零写回”发生（server/engine.go:1786-1804 → manager.go:2230），指令硬编码在 agent/planner.go:257；其余终态无沉淀。terminalreason.go:121 只给 UI 标签。

建议：在 runIntent 终态落库点（server/engine.go:1722-1800）确定性写 reflection 节点（新 kind 或 fact 子类型），字段固定：intent_id、dimension、hypothesis/success_criteria、terminal reason、写回计数、工具调用分布、Guard 拦截次数、失败特征摘要。planner 的 renderTriggers 与 graphOverviewData 增加 recent_lessons；worker 启动由 priorFactsBlock（worker.go:773）带入同资产/同维度最近 lesson。这样反思不依赖模型是否愿意反思，也无需额外 LLM 调用；需要 LLM 总结再挂 reporter/专用 agent。

落点：server/engine.go:1722-1810、db/exploration.go:208（AddNode）、agent/planner.go:195、agent/tools.go:506/738、agent/worker.go:773、agent/terminalreason.go。验收：每个终态意图都能查到 lesson；planner 下轮无须 get_worker_trace 就能看到上次失败特征。

### 改进 3：跨任务记忆从“成功 playbook 单点”扩展为成功+失败经验库，并注入 worker

现状 playbook 只覆盖 validator PASS 的 critical/high（agent/tools.go:2119），只注入 planner Top3（agent/variant.go:106、db/playbooks.go:230），匹配键 vulnclass/techs/root_domain 精确交集；worker 看不到跨任务先例；失败路径只在各任务 activity。

建议：把 playbooks 扩成 experiences（或加 outcome 维度）：记录成功链与失败/负向结论（终态按 dimension + asset simhash + 失败特征写入），检索支持“同 simhash 簇/同技术栈/同维度”混合排序，在 worker.execute system 尾部（紧邻 priorFactsBlock）注入 3 条最相关经验；给 worker/main 一个只读 search_experience 工具按需检索。利用已有 simhash/SimilarHTTPEndpoints（server/assembly.go:311-320）。

落点：db/playbooks.go、agent/variant.go、agent/worker.go、agent/tools.go（WorkerTools 增加只读工具）、server/assembly.go、server/engine.go（终态写入）。验收：同一技术第二次尝试能看到上次失败特征；playbook UsedCount 回流成排序信号。

### 改进 4：工具路由学习：把 tool_usage / skill_usage / guard 归因变成 prompt 先验与过滤信号

现状工具选择靠静态文案（agent/ops_tails.go:12/40）；系统已在记录 tool_usage（db/tool_usage.go:16、server/tool_usage.go:29）、skill_usage（db/skill_usage.go:30、server/skill_usage.go:35）、Guard per-tool blocked/error（guard/guard.go:268），但只用于统计页/planner 态势。

建议：新增聚合查询（dimension × tool / dimension × skill × 结果），产出“某维度最常成功/高 error/被拦最多”的手段，两个消费点：
1. worker 启动按意图 dimension 注入 3-5 条“有效手段”（替换/补充静态 routing）；
2. ToolResolve（server/assembly.go:403）对高 error/高 blocked 工具做描述标注或降权（不硬删），对长期未命中 skill 名用 MissingSkillStats（db/skill_usage.go:106）修正索引。

落点：db/tool_usage.go、db/skill_usage.go、新增 db/tool_stats.go、server/tool_usage.go、agent/worker.go:393、agent/planner.go:424、server/assembly.go:403、agent/ops_tails.go。验收：同维度“工具 A 连续 error”能被下一轮 prompt 反映；skill 误名率从 MissingSkillStats 观测下降。

### 改进 5：成本预算从“意图级”升级为“任务级 + 角色级”预算网关，并驱动模型降级

现状唯一预算闸是意图级 token/分钟（server/engine_guard.go:121/235）与 auto_finish_max_rounds=80（server/auto_finish.go:23）；planner 轮/压缩/reporter/复测不在预算内；llm_usage 事后台账（db/llm_usage.go:439 UsageByTask），estimateTokens 只用于 pool 窗口（llmpool/pool.go:282）。

建议：
1. Engine 维护任务预算（tokens/USD/墙钟），从 UsageByTask + cost.go:42 初始化/滚动；
2. plannerLoop 每轮开始（engine.go:1245 附近）与 runIntent 前检查，80% 时通过 taskLLMRuntime（task_llm.go:123）切便宜/可用 profile，100% 时 settleTaskWithReason("budget") 并要求 planner 最后判定；
3. 预算态势进 stallOverview（agent/tools.go:3123），让 planner 学会“预算紧→收敛打穿，不开新长链”。

落点：server/engine_guard.go、server/engine.go、server/auto_finish.go、server/task_llm.go、db/llm_usage.go、server/cost.go、agent/tools.go:3123。验收：任务级预算耗尽终态原因可区分于 timeout；模型切换在 llm_transition activity 可审计（task_llm.go:803）。

## 5. 建议实施顺序（结合现有代码）

1. **覆盖率矩阵**（改进 1）：统一四处口径，收益最大、风险最低，且能直接改善 planner 派单与报告。
2. **终态 reflection 节点**（改进 2）：确定性写入，无额外 LLM 成本，立刻让 planner 看到“上次为什么失败”。
3. **任务级预算网关**（改进 5）：直接降本，且可复用现有 llm_usage/cost/profile 切换。
4. **经验库扩展**（改进 3）：成功+失败、worker 注入、simhash 检索；依赖前两步的数据。
5. **工具路由学习**（改进 4）：最后做，需要积累 tool_usage/skill_usage 样本。

独立 Auditor 角色（行业最强共识之一）可作为一个跨批次专项：在现有 verification_depth/validate_finding 之上新增只读 auditor agent + verification_strategy 枚举，不急于一次做完。
